# ai-prd-reviewer

## 使用场景

当你已经有 AI 功能想法、PRD 草稿、产品说明、原型描述或准备交给 Codex/Claude Code/Cursor 的需求文档，希望判断它是否已经足够清晰、可落地、可评测、可交接时，使用这个 skill。

这个 skill 不是 PRD 生成器。它的重点是审查：

> 这份 AI PRD 是否真的能指导产品、设计、开发、prompt 和测试把功能做出来？

适合审查：

- AI 产品 PRD。
- AI 功能需求草稿。
- AI Agent / 多角色 / Copilot / AI Coding 功能说明。
- 准备交给 AI Coding 工具的产品需求。
- 已经有 demo，希望倒推成更完整需求的项目。

## 输入材料

尽量提供以下信息。缺失时，先基于已有材料评审，并在报告中列出“必须补充的问题”。

- 产品背景。
- 目标用户。
- 用户问题或使用场景。
- AI 功能描述。
- 当前 PRD 或需求草稿。
- 用户输入与 AI 输出样例。
- 页面、流程或交互描述。
- 模型、工具或技术限制。
- 业务限制、风险限制或上线目标。

## 工作流程

### Step 1: 识别 PRD 类型

先判断这份文档要服务什么目标。

常见类型：

- **探索型 PRD**：验证一个 AI 产品机会是否成立。
- **功能型 PRD**：定义一个具体 AI 功能如何实现。
- **Agent 型 PRD**：定义多步骤任务、工具调用、权限和人工确认。
- **多角色型 PRD**：定义角色分工、发言顺序、冲突处理和汇总。
- **AI Coding 交接型 PRD**：让 coding agent 可以直接拆任务和实现。
- **迭代型 PRD**：基于已有 demo，补齐体验、边界和验收。

### Step 2: 判断核心产品问题

先判断 PRD 有没有说清楚：

- 用户是谁。
- 用户在什么场景下遇到什么问题。
- 为什么需要 AI。
- AI 相比普通功能带来的独特价值是什么。
- 成功体验是什么样。

如果这些没说清楚，不要急着审查功能点。

### Step 3: 使用 AI PRD 8 层审查框架

按 8 层评估，每一层都要给判断、缺口、影响和补充建议。

1. **问题与目标**：用户问题、产品目标、成功体验是否清晰？
2. **核心 AI 体验**：AI 的价值是否成立？是生成、理解、推荐、总结、执行，还是多角色协作？
3. **输入/输出契约**：用户输入、上下文、AI 输出格式、结果状态是否定义清楚？
4. **模型行为边界**：AI 应该做什么、不该做什么、不确定时怎么处理？
5. **交互流程与状态**：加载、确认、编辑、追问、撤回、重试、空状态和失败状态是否完整？
6. **风险与兜底**：幻觉、误导、高风险建议、权限、隐私、人工介入是否处理？
7. **评测与验收**：怎样判断 AI 输出好坏？有没有样例、bad case、验收标准？
8. **交接与实现就绪度**：开发、设计、prompt、测试、AI Coding 工具是否能据此行动？

### Step 4: 区分缺口类型

每个问题都要标记属于哪一类：

- 产品缺口：目标、用户、场景、价值不清。
- 体验缺口：流程、状态、控制、反馈不清。
- AI 行为缺口：模型边界、输出规则、失败策略不清。
- 评测缺口：没有样例、指标、验收标准。
- 交接缺口：无法直接给设计、开发或 AI Coding 工具执行。

### Step 5: 输出可补进 PRD 的文本

不要只说“需要补充”。必须给出可直接粘贴进 PRD 的补充段落、表格或验收标准。

## 质量标准

好的输出应该：

- 不把 PRD 当普通功能文档审查，必须审查 AI 特有内容。
- 能判断 AI 体验是否真的成立，而不是只检查格式完整。
- 能指出 PRD 缺口会如何影响设计、开发、prompt、测试或 AI Coding。
- 每个 P0/P1 缺口都要包含负责人和验收标准。
- 必须给出可以直接粘贴进 PRD 的补充文本。
- 必须说明哪些内容已经可以交给 AI Coding，哪些还不能。

差的输出通常表现为：

- 只说“需求不够清晰”，但不说明缺什么。
- 只套传统 PRD 模板，不检查模型行为和输出质量。
- 只生成新 PRD，不审查原 PRD。
- 没有评测、验收、bad case 或失败状态。
- 没有区分产品缺口、体验缺口、AI 行为缺口和交接缺口。

## 示例：多角色 AI 产品应该重点审什么

如果审查一个“名人智囊团”类 PRD，重点不是只看有没有页面和按钮，而是检查：

- 用户为什么需要多位名人，而不是一个 AI 助手？
- 角色选择规则是否清楚？
- 每位角色的输出质量标准是什么？
- 多角色之间如何产生观点碰撞？
- 主持人汇总如何比单个回答更有价值？
- 用户是否可以换人、追问、重写、纠错？
- 高风险问题下如何避免替用户做不可逆决定？
- 怎样验收“一次回答是深刻的、现实的、有帮助的”？

## 不适用场景

不适合用来：

- 替代完整市场调研。
- 生成详细技术架构。
- 评估底层模型参数。
- 审查 RAG 检索方案。
- 替代法律、医疗、金融等专业审查。

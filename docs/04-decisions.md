# Decisions

## D001: 项目名称暂定为 AIPM Core Skills

日期：2026-05-26

决定：项目名称暂定为 `AIPM Core Skills`。

原因：

- 名称直接表达项目面向 AI 产品经理。
- `Core Skills` 表达这是基础能力包，而不是单个提示词。
- 后续可以根据 owner 个人品牌再调整。

## D002: 首版只做 5 个 skills

日期：2026-05-26

决定：首版只做：

- `ai-ux-review`
- `ai-prd-reviewer`
- `agent-fit-analyzer`
- `badcase-diagnosis`
- `ai-coding-handoff`

原因：

- 这 5 个方向和 owner 的经验最贴近。
- 数量足够展示完整能力，但不会过度分散。
- 每个 skill 都可以连接真实项目案例。

## D003: 暂不做 RAG

日期：2026-05-26

决定：暂不做 RAG 相关 skill。

原因：

- RAG 技术深度较高。
- 面试时容易被追问到切片、召回、重排、向量库、权限和评测。
- 当前阶段更适合聚焦 AI 产品体验、Agent 适用性、Bad Case 和 AI Coding 协作。

## D004: 文档中文为主

日期：2026-05-26

决定：首版文档中文为主。

原因：

- owner 当前最需要的是自己能理解、能复盘、能讲清楚。
- 中文更适合沉淀真实项目思考。
- 后续开源国际化时，可以再补英文 README 或英文版 skill。

## D005: ai-ux-review 聚焦 AI 产品体验，不做通用 UI/UX 审美

日期：2026-05-26

决定：`ai-ux-review` 的核心定位是审查 AI 产品的信任、控制、透明、失败恢复和风险表达，不与通用 UI/UX skill 竞争风格库、配色、组件和技术栈覆盖。

原因：

- GitHub 上已有高星通用 UI/UX skill，覆盖设计系统、颜色、字体、技术栈和通用 UX guideline。
- 通用网站审查类 skill 已经覆盖 vibe-coded 视觉反模式。
- 但 AI 产品体验里的不确定性、可控性、失败兜底和高风险措辞仍然是明显空位。
- 这个切口更能体现 owner 的 AI 产品经理和体验设计结合能力。

## D006: ai-ux-review 升级为通用 AI 产品体验评估框架

日期：2026-05-26

决定：`ai-ux-review` 不再只作为风险审查 skill，而是升级为通用 AI 产品体验评估框架。

新框架先识别产品类型和核心体验承诺，再用 8 层通用框架评估：

- 核心价值
- 输入质量
- 理解质量
- 输出质量
- 过程体验
- 汇总与落地
- 用户控制与恢复
- 风险与边界

原因：

- AI 产品体验不能只从风险角度评估。
- 很多 AI 产品的核心价值在于洞察、启发、效率、协作或执行，而不是免责声明。
- 对名人智囊团这类产品，最核心的是输出是否深刻、多角色是否有碰撞、最终汇总是否有现实意义。
- 这个框架更能体现 owner 的 AI 产品经理判断力。

## D007: 每个核心 skill 都必须配真实项目案例

日期：2026-05-26

决定：后续第 3、4、5 个 skill 也沿用同一方法论：每个 skill 除了 `SKILL.md`，还要配一个真实项目案例，并在案例开头说明它展示了该 skill 的哪些能力。

原因：

- 开源项目不能只展示方法论，还要展示真实项目上的使用效果。
- 真实案例能帮助别人快速理解 skill 的价值。
- 对 owner 的个人主页和面试更有说服力。
- 案例可以侧面展示 owner 已经做过真实 AI 项目，而不是只做提示词整理。

## D008: ai-coding-handoff 不做任务管理系统

日期：2026-05-26

决定：`ai-coding-handoff` 的定位是“AI PM 到 AI Coding 的任务交接器”，不是 TaskMaster、看板、自动执行框架或 session memory 系统。

原因：

- 市面上已经有 Claude Task Master、spec-driven development、AI handoff、project memory 等工具。
- 本项目的差异化不是管理任务状态，而是把产品判断翻译成 Codex、Claude Code、Cursor 能执行的任务包。
- owner 更需要展示 AI PM 能力：判断哪些需求能交给 AI Coding、如何拆范围、如何写验收标准、如何保护现有项目不被乱改。

执行方式：

- 每个 handoff 输出都要包含：任务目标、涉及文件、实现要求、不做什么、验收标准、测试计划、需要 owner 确认的问题。
- 不引入复杂项目管理工具。
- 不把产品方向决策交给 AI Coding 工具自行决定。

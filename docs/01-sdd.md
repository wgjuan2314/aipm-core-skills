# Skill Design Document

本项目中的 SDD 指 Skill Design Document，不是传统软件工程里的 System Design Document。

SDD 的作用是定义每个 skill 应该如何设计、如何输出、如何判断质量。

## Skill 设计原则

每个 skill 都必须满足以下原则：

- 解决一个明确的 AI 产品经理工作场景。
- 输入材料要清楚，不能假设用户知道怎么准备。
- 输出格式要稳定，方便复制到文档、GitHub issue、作品集或 AI Coding 工具。
- 要有质量标准，能判断输出是好还是坏。
- 要说明不适用场景，避免被误用。

## 标准结构

每个 `SKILL.md` 使用以下结构：

```markdown
# Skill 名称

## 使用场景

## 输入材料

## 工作流程

## 输出格式

## 质量标准

## 示例

## 不适用场景
```

## 输入设计

每个 skill 的输入材料应该尽量使用自然语言，不要求用户懂复杂技术。

常见输入包括：

- 产品想法。
- 用户场景。
- PRD 草稿。
- 页面截图描述。
- AI 输出样例。
- 失败案例。
- 目标用户。
- 业务限制。
- 技术限制。

## 输出设计

输出要适合真实工作使用，而不是只给一个漂亮总结。

推荐输出包括：

- 结论。
- 问题清单。
- 风险等级。
- 修改建议。
- 下一步行动。
- 可复制的任务描述。

## 质量标准

好的 skill 输出应该满足：

- 具体，不空泛。
- 能指出真实风险。
- 能给出可执行下一步。
- 能帮助 owner 在面试中讲清楚产品思考。
- 能帮助 AI Coding 工具继续执行。

差的 skill 输出通常表现为：

- 只说原则，不给判断。
- 只夸项目，不指出风险。
- 输出太长但没有行动价值。
- 使用过多 owner 不熟悉的深技术术语。

## 首版验收标准

首版每个 skill 至少要具备：

- 一个完整 `SKILL.md`。
- 一个真实项目案例，案例开头必须说明它展示了该 skill 的哪些能力。
- 一个清晰输出格式。
- 一个不适用场景说明。

## 真实案例规范

从 v0.2 开始，每个核心 skill 都要配一个 `examples/` 下的真实项目案例。

案例必须包含：

- 被评审/评估项目的背景。
- 使用的 skill。
- 参考了哪些项目文件或输入材料。
- “这个案例展示了什么”小节。
- 真实评审结果。
- 可执行建议或可复制文本。

案例的目的不是证明项目完美，而是展示 skill 的实际判断力。

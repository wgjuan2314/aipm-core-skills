# AI Coding Handoff: 名人智囊团

> 这是 `ai-coding-handoff` 的真实项目交接案例。
>
> 被交接项目“名人智囊团”是项目 owner 真实开发过的 AI 微信小程序：用户输入一个决策困惑，系统自动匹配 3 位名人角色，生成独立回答、辩论、追问、主持人汇总和行动计划。
>
> 这个案例展示如何把前面 PRD 评审和 bad case 诊断里的产品判断，转成 Codex、Claude Code 或 Cursor 可以执行的任务包。

## 0. 这个案例展示了什么

这个案例展示 `ai-coding-handoff` 的 5 个核心能力：

1. **判断哪些需求能直接交给 AI Coding**：不是所有 backlog 都能直接开写。
2. **把产品语言翻译成开发任务**：例如“更安全”会被拆成高风险识别、prompt 规则、回归测试。
3. **写清楚不做什么**：减少 AI Coding 顺手大改架构、重构无关页面或引入复杂依赖。
4. **把验收标准前置**：让 AI Coding 做完后知道怎么自检。
5. **保留 owner 决策权**：高风险边界、语气取舍、是否牺牲戏剧性，仍由 owner 判断。

## 1. 交接结论

- 是否可直接交给 AI Coding：部分可以。
- 建议执行方式：拆成 4 个小任务逐个交接，不要一次性交给 AI 做“大优化”。
- 风险等级：中。
- 一句话说明：名人智囊团的高风险边界、主持人汇总、反馈入口和 golden set 字段都可以交给 AI Coding，但“产品更犀利还是更稳健”的取舍需要 owner 先确认。

## 2. 背景与目标

- 产品背景：名人智囊团通过多角色回答、辩论、追问、主持人汇总和行动计划，帮助用户获得决策启发。
- 用户问题：遇到辞职、投资、关系等高风险问题时，产品不能只给“犀利观点”，还要保持可信、可控、可恢复。
- 本次目标：把 bad case 诊断中的 3 个改进点转成可实现任务：高风险问题兜底、主持人汇总升级、回答反馈入口、golden set 字段补充。
- 不做什么：
  - 不重构小程序整体架构。
  - 不迁移云函数。
  - 不接入 RAG。
  - 不更换模型。
  - 不重写全部名人 prompt。

## 3. 任务拆解

| 优先级 | 任务 | 目标 | 是否可直接执行 |
| --- | --- | --- | --- |
| P0 | 高风险问题识别与 prompt 兜底 | 防止辞职、投资、法律、医疗等场景输出绝对建议。 | 可以 |
| P0 | 主持人汇总 prompt 升级 | 让汇总从“复述观点”变成“真正问题、关键分歧、现实约束、下一步验证”。 | 可以 |
| P1 | 回答卡反馈入口 | 让用户标记“不像他、太绝对、没帮助”，沉淀 bad case。 | 可以，但需要确认数据存哪里 |
| P1 | 黄金评测集字段补充 | 给 bad case 增加失败类型、修复规则和回归期望。 | 可以 |

## 4. 推荐交给 AI Coding 的任务包

### Task 1: 增加高风险问题识别与 prompt 兜底

**目标**

当用户问题涉及辞职、投资、借贷、法律、医疗、心理、亲密关系、转账、辞退等高风险决策时，名人回答、辩论、汇总和行动计划不得给出单一路径的绝对建议。

**建议先阅读**

- `CLAUDE.md`
- `docs/API.md`
- `docs/SDD.md`
- `miniprogram/pages/index/index.js`
- `miniprogram/utils/celebrities.js`

**可能涉及文件**

- `miniprogram/pages/index/index.js`
- `docs/API.md`
- `docs/SDD.md`

**实现要求**

- 新增一个轻量函数，例如 `detectRiskLevel(question)`。
- 先用关键词规则实现，不接入复杂分类模型。
- 命中高风险时，在名人回答、辩论、汇总、行动计划 prompt 中追加保守规则。
- 保守规则包括：
  - 不给“立刻辞职 / 马上投资 / 必须分手”等绝对建议。
  - 先列出关键补充变量。
  - 至少给两个可选路径。
  - 给一个 24-72 小时内可执行的小步验证动作。
- 保留原本“有活人感、犀利、非 AI 腔”的表达风格。

**不要改动**

- 不改页面主流程。
- 不改名人库结构。
- 不改 API provider。
- 不新增后端。
- 不把所有问题都变成免责声明。

**验收标准**

- 输入“我要不要辞职去创业”，输出不应直接建议辞职或不辞职。
- 输入“我有 50 万，要不要重仓朋友推荐的项目”，输出应强调能力圈、风险、信息不足或小步验证。
- 普通低风险问题仍能保持犀利和角色感。
- 控制台无报错。

**测试计划**

- 手动测试 5 个高风险问题。
- 手动测试 3 个普通启发问题，确认没有过度保守。
- 检查历史记录仍能保存回答、汇总和行动计划。

**完成后需要更新的文档**

- `docs/API.md`
- `docs/SDD.md`

### Task 2: 主持人汇总 prompt 改成四段式

**目标**

让主持人汇总稳定输出：

1. 真正的问题。
2. 关键分歧。
3. 现实约束。
4. 下一步验证。

**建议先阅读**

- `CLAUDE.md` 的汇总调用说明。
- `miniprogram/pages/index/index.js` 中生成汇总的函数。
- `examples/ai-ux-review-celebrity-council-v2.md` 对汇总质量的评估。

**可能涉及文件**

- `miniprogram/pages/index/index.js`
- `docs/API.md`
- `docs/SDD.md`

**实现要求**

- 修改汇总 prompt，不改 UI 结构。
- 输出仍保持 150-220 字以内，适配当前时间线展示。
- 汇总必须提炼“真正分歧”，而不是简单说各方都有道理。
- 下一步验证必须是低风险、具体、明天能做的小动作。

**不要改动**

- 不新增页面。
- 不改时间线数据结构，除非现有渲染无法承载。
- 不改历史详情页逻辑。

**验收标准**

- 汇总中能看到四个信息点。
- 对“辞职创业”这类问题，下一步不是“辞职”，而是低风险验证。
- 对普通问题，汇总不显得过度安全或模板化。

**测试计划**

- 用“我要不要辞职创业”测试。
- 用“我做的 AI 产品没人用怎么办”测试。
- 用“怎么提升学习效率”测试。

**完成后需要更新的文档**

- `docs/API.md`
- `docs/SDD.md`

### Task 3: 回答卡增加轻量反馈入口

**目标**

让用户能标记某条回答的问题，方便后续沉淀 bad case。

**建议先阅读**

- `miniprogram/components/answer-card/answer-card.wxml`
- `miniprogram/components/answer-card/answer-card.js`
- `miniprogram/pages/index/index.js`
- `miniprogram/utils/history.js`

**可能涉及文件**

- `miniprogram/components/answer-card/answer-card.wxml`
- `miniprogram/components/answer-card/answer-card.wxss`
- `miniprogram/components/answer-card/answer-card.js`
- `miniprogram/pages/index/index.js`
- `miniprogram/utils/history.js`

**实现要求**

- 在每张回答卡底部增加 3 个轻量反馈项：`不像他`、`太绝对`、`没帮助`。
- 点击后给出已记录状态。
- 反馈数据先保存在本地历史记录中，不接后端。
- 同一条回答可以只记录一个反馈类型，避免复杂化。

**不要改动**

- 不新增登录。
- 不接云数据库。
- 不做复杂分析 dashboard。
- 不影响分享图生成。

**验收标准**

- 用户点击反馈后，UI 有明确状态变化。
- 重新进入历史详情时能看到反馈结果，或至少数据已保存在历史记录中。
- 未点击反馈时不影响原回答展示。

**测试计划**

- 首页回答卡点击反馈。
- 进入历史详情检查数据。
- 删除历史记录后不报错。

**需要 owner 先确认**

- 反馈是否需要在历史详情页展示。
- 反馈文案是否就用“不像他 / 太绝对 / 没帮助”。

**验收标准**

## 5. 需要 owner 先确认的问题

- 高风险问题下，产品是否愿意牺牲一点“名人犀利感”，换取更稳健的建议？
- 反馈入口是否要出现在 MVP 里，还是先只写进 backlog？
- 历史详情页是否需要展示反馈结果？
- 高风险问题识别第一版是否接受关键词规则？
